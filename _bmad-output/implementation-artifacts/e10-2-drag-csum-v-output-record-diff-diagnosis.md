# Story 10.2: Drag `CSUM -V` output onto the detail view — record diff + diagnosis

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a MicroBeast daily driver,
I want to select the Beast's `CSUM -V` output in the terminal and drop it onto a file's detail view to see exactly which records differ and the likely cause,
so that "the file is corrupt" becomes "block 0041–0048 never got written back" without leaving the terminal or running `diff`.

This is the **second and final** story of Epic E10. S10.1 shipped (commit 010aa81): the ambient CRC-32 column, the `⁞` detail sub-state with its per-record Fletcher-16 listing, and an **explicitly interim** rule that a terminal-selection drop while the detail view is open is refused. This story replaces that refusal with the diff routing it was holding the door for: drop the Beast's own `CSUM -V` output onto the open detail view → per-record diff → one-line damage-pattern diagnosis (the `beast_csum` README table, alive in the UI). Nothing touches the wire.

## Scope boundary (read first)

**IN scope (S10.2):** the pure `CSUM -V` parser + mismatch-pattern classifier (in `csum.js`, injected); the detail-open drop route (affordance, parse, diff, captions, diagnosis, failure state); un-hiding the S10.1 detail footer hint; the bloom/affordance composition changes that routing forces; specs; the UX-contract dated amendments.

**OUT of scope — do NOT build here:**
- **Any change to the S9.3 pull path when no detail is open.** A selection drop with the detail closed behaves byte-identically to shipped S9.3 (review → confirm → `SLIDE S …`). Its specs must stay green untouched.
- **Any wire traffic.** The diff path never calls `pushTxBytes` / `onPullRequested` / `sendFiles`. It is NOT suspended by SLIDE wire-ownership (it compares text, not the port) — that is a requirement, not an accident (FR-11).
- **Any change to `input/selection.js`, `input/file-source.js`, `transport/slide.js`, `input/tx-sink.js`**, anything Rust/wasm. `main.js` gains exactly two injected opts (the parser + classifier, per AD-3).
- **The "everything shifted by a constant" README pattern.** The epic deliberately ships three diagnosis lines + the count-mismatch report; the shift pattern is not in FR-8. Do not add it.
- **Diff persistence / re-diff on refresh.** A diff is painted once per drop and replaced by the next drop; `‹ Back` discards it. No caching, no auto-refresh of a painted diff.
- **New colors/tokens.** `--chrome-*` only (AD-9); **never red**, never colour alone (UX-DR4 — red stays reserved for security/port-lost).

## Acceptance Criteria

1. **Pure parser, injected not imported (FR-6, FR-10, NFR-2).** `www/renderer/csum.js` gains named export `parseCsumV(text) → { records: Map<number,string>, count: number, crc: string|null }`. Grammar (pinned by `csumhost.c:80,86` — `"%04X: %04X\n"` records, `"%08lX\n"` CRC — and the real capture `../beast_csum/pc.txt`): split on `/\r?\n/`, trim each line (terminal grid selections carry trailing spaces); a record line is exactly 4 hex digits, `:`, one-or-more spaces, 4 hex digits (case-insensitive, values normalized uppercase); the device CRC is the LAST line that is exactly 8 hex digits (null if none — the CRC clause of the caption then drops, AC-6); everything else — the echoed `CSUM -V FILE.COM` command line, `A>` prompts, blank lines — is ignored (the DIR-column-merge tolerance class: narrow rules, everything unmatched flows past). Duplicate record indices: last occurrence wins. `count` = number of distinct record indices. The module stays pure (no DOM, no I/O, no imports); `pull-pane.js` receives `parseCsumV` as a `wirePullPane` opt injected by `main.js`, unguarded (the S9.2/S10.1 fail-loud convention, pull-pane.js:89-108).
2. **Pure pattern classifier (FR-8, NFR-2).** `csum.js` gains named export `classifyCsumDiff({ hostCount, deviceCount, mismatched }) → { kind: 'count'|'tail'|'run'|'stride'|'none', n?: number }` where `mismatched` is the sorted array of differing compared indices. Precedence, first match wins: (a) `deviceCount !== hostCount` → `'count'` — and the pattern classifier goes no further: the count mismatch IS the named cause, no second diagnosis renders over it; (b) no mismatches → `'none'`; (c) exactly one mismatch at index `hostCount - 1` → `'tail'`; (d) one contiguous run of length ≥ 2 → `'run'`; (e) an arithmetic progression with stride `n ≥ 2` and ≥ 3 members → `'stride'` with `n`; (f) else `'none'` (a single mid-file mismatch names no pattern — per-record results carry it). Injected beside the parser (second new opt, same convention).

## Dev Notes

### The output being parsed (ground truth)

`csumhost.c:80` prints records as `printf("%04X: %04X\n", rec_no, fletcher16(...))`; `:86` prints the CRC as `printf("%08lX\n", crc)`. The real capture `../beast_csum/pc.txt` confirms: 210 record lines `NNNN: VVVV` then one bare `6EC586BD`. The Z80 CSUM.COM prints the same grammar to the terminal (CR/LF line ends — hence `/\r?\n/`). On screen the user's selection will also carry: the echoed command (`A>CSUM -V FILE.COM` — with or without a space after the prompt), a trailing `A>` prompt, blank lines, and 80-column trailing spaces from grid selection. That is the whole tolerance envelope — keep the rules narrow (the `mergeDirColumns` discipline, :1169-1201): a strict record regex plus per-line trim covers all of it without heuristics. **Do not use `../beast_csum/z80.txt` as a fixture** — it is a stale debug capture whose record indices are all `0000`.

### Why the host records need stowing (and why that is sanctioned)

S10.1's code review deliberately stopped retaining the records array in `state.detail` ("the DOM is the listing's single home; hook keeps `recordCount`") and listed "caching the detail's records" as S10.2's call. This story makes that call: `openDetail` stows the analyzed `records` in a module-scope `detailRecords` beside the flag, because the diff must compare against **exactly the listing painted** — re-reading the file at drop time could diff against bytes the user isn't looking at (the file may have changed since open; the detail is deliberately never repainted by refreshes). Scraping the DOM rows back apart would be the only other source and is strictly worse. Cleared wherever the detail clears.

### Diff model (keep it this simple)

`parseCsumV` returns a sparse `Map` keyed by record index — a partial selection parses fine. Compared set = host indices `0..hostCount-1` that have a parsed device value; `m` = its size; mismatches = compared indices whose values differ. `count ≠ hostCount` → the count line (and classifier kind `'count'`, which suppresses any pattern line — one named cause at a time; a truncated device listing "matching" the tail pattern would mislead). Host CRC for the caption clause is `state.detail.crc` (the header the user is reading). Empty-file detail (`hostCount === 0`): any parsed records → `m = 0` → no caption, count line only.

### Where the diff paints (and what it must not touch)

`renderDetail` (:1127-1151) built one `.pp-dv-row` per record with textContent `NNNN: VVVV` (`hex4` :1153). `renderDiff` mutates those rows in place: add/remove `mismatch` class, set base text + append the `≠ DDDD` suffix span for mismatches, restore plain text for previously-marked rows on a re-drop, preserve `detailRowsEl.scrollTop`. It is called ONLY from the drop path — `render()` (:1350-1416) keeps projecting visibility only, so the existing no-repaint-under-refresh guarantees (S10.1 spec (h)) extend to the diff for free. The result region sits between `‹ Back` and the rows (index.html markup :2153-2157; the detail CSS block is :672-720) so caption + diagnosis are visible without scrolling a long listing.
