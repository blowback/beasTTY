# Story 9.4: Reverse drag — pane file to terminal to device (optional)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a MicroBeast daily driver,
I want to drag a file out of the pane onto the terminal to send it to the device,
so that both directions of transfer live in-app, not just OS-filer to device.

This is the **fifth and final** story of Epic E9, and it is optional (FR-12 is a bonus; the sprint note says "may be cut from v1"). S9.1a–S9.3 shipped the whole pull direction and passed UAT-E9-01 on real hardware (2026-07-24). This story closes the loop in the other direction with the thinnest possible slice: pane rows become native drag *sources* whose payload is the row's real `File`, and the existing terminal file-drop path does everything else. There is no new transport, no new modal, no new review surface — the deliverable is one well-behaved dragstart.

## Acceptance Criteria

1. **Draggable file rows (FR-12 origination).** In list view every `.pp-row` is a native drag source: `draggable = true` plus `dataset.name` for the delegated handlers. Enumeration keeps each entry's file handle — `state.files` entries become `{name, size, handle}` (pull-pane.js:334-338) — **without** changing the diff-render snapshot semantics (snapshot stays keyed on name+size; a handle identity change alone must not count as a content change) and without leaking handles into `__getStateForTests().files` (existing specs deep-compare it). Fresh rows drag the same as plain rows. Nothing else is draggable: header, footer, rail, buttons, and the first-run/permission/empty views are untouched.
2. **Stash at pointerdown, payload at dragstart.** A primary-button pointerdown on a row begins resolving that row's `File` (`entry.handle.getFile()`) into a module stash `dragOut = {name, file: null|File}`. No `setDragImage` override — the default ghost for a drag originating on the row is the row itself, which is small and correct (S9.3's canvas-screenshot problem does not apply). dragend always clears the stash and restores focus to the injected `terminalWrapper` (a row pointerdown necessarily blurs it — see Dev Notes "Focus").

## Dev Notes

### Why `items.add(File)` and not a new entry point (read before T2)

Two designs satisfy the epic AC ("resolved to a `File` via `getFile()` and handed to the existing `file-source.js` send path"):

- **(a) Native payload — chosen.** Put the real `File` in the drag's data store at dragstart. `file-source.js`'s four wrapper handlers key off `dataTransfer.types.includes('Files')` (:261-263) and nothing else — they cannot tell this drag from an OS drag, so the overlay affordance, session chip-flash, validation, 8.3 truncation, collision scheme, confirm modal (with its `slideConfirmTransfers` silent path), and every `enterSendMode` refusal arrive with **zero code changes** to any transport file. The story's whole diff is pull-pane.js + one CSS line + specs.
- **(b) Programmatic handoff — sanctioned fallback only.** Export a `sendFiles(files)` wrapper over the private `processFiles` (file-source.js:343), drive an S9.3-style pointer-event drag from the pane, and call it on drop-over-wrapper. More moving parts, a new public API on file-source.js, a hand-rolled drop hit-test — take it only if the T5 manual checkpoint shows the native payload does not survive Chromium's real drag loop, and record the deviation. Keep the pane-side surface (`dragOutArmed`, specs) identical so the swap is contained.

### The risky part — an async `File` and a synchronous dragstart

`dataTransfer` accepts data only synchronously inside the dragstart handler, but `handle.getFile()` is async. Hence the stash: pointerdown starts the resolve, dragstart consumes it. In practice a local `getFile()` resolves in well under the pointer-travel time that precedes dragstart, but the race is real, so the losing branch is specified (AC-2): cancel the drag, never send a half-armed payload. Two hygiene rules: (1) a resolve that lands after dragend must find `dragOut` already null and do nothing (identity-check the stash object, don't just null-check); (2) the stash holds a `File` snapshot — never cache it across drags; re-resolve per gesture so a file replaced on disk between drags sends fresh bytes.

Chromium supports `DataTransferItemList.add(File)` in dragstart and exposes it to same-document drop targets via `dataTransfer.files` — the synthetic specs prove the handlers end-to-end, but only the T5 manual run proves the real drag loop (same epistemic split as S9.3's origination checkpoint).

### Focus — why rows are the sanctioned retainFocus exception

`retainFocus` keeps terminal focus by `preventDefault()` on mousedown (ARCHITECTURE-SPINE.md AD-10, :116-119). Preventing mousedown's default also suppresses native drag initiation — S9.3 documented this from the canvas side, and it applies identically here. So rows stay bare: a row pointerdown blurs `#terminal-wrapper` (today's behavior for any pane click outside the retainFocus-wired buttons — this also means D-19 clears any live terminal selection, which is pre-existing pane-click behavior, not a regression). Recovery is two-layered: dragend refocuses the wrapper (AC-2), and a completed drop hands focus to the send modal whose existing close paths restore per `restoreTo` (send/first-only → wrapper). Comment the exception at the pointerdown handler citing AD-10 and this story.

### Coexistence — three drop targets, no crosstalk

- **Terminal wrapper (file-source.js):** consumes the reverse drag as designed. Its session guard (`isSessionActive`, :265-270) covers pending/active *send*; the recv direction is covered by our drag-side suspension (AC-4) and, at the last line of defense, `enterSendMode`'s wire-owner refusal (slide.js:1016-1020). Do not "fix" the asymmetry in file-source.js — out of scope.
- **The pane itself:** `dropAcceptable()` requires `selDrag.active` (pull-pane.js:464-468) — set only by the terminal-selection drag observer chain, never by a reverse drag. AC-5 asserts it.
- **selection.js:** owns canvas pointer handlers and the selection-drag origination; a reverse drag never produces a canvas pointerdown, and no pointerdown can occur mid-drag. Its `data-drop-target` early-return (:113-121) is the file overlay's contract — untouched.
- **Bloom edge (accepted, not built):** dragging a row out of a bloomed card (narrow window) leaves the bloom up after the drop; the next pointerdown outside the pane dismisses it, per S9.3's existing rules. Do not add an un-bloom-on-reverse-drag path; note it in the UAT section if it reads oddly in practice.

- **UAT-E9-03 hardware failure diagnosis (2026-07-24, Ant's multi-file drag: bbcbasic.com 19 KB + mbasic.com 24 KB — file 1 OK, file 2 never started, "Transfer cancelled by peer", chip stuck).** Investigation path: instrumented the send flow, then read the upstream Z80 source (github.com/blowback/slide slide.asm) and the reference PC client (slide-py/send.py). Ruled out: the Z80's deaf `close_file` window (already mitigated by the existing 500 ms inter-file drain delay); the create-window (Z80 ACKs the header only AFTER creating the file); Z80-side per-frame issues. Root cause found by inspection and reproduced byte-exact in a spec: `dispatchSendMode`'s byte classifier is stateless across chunks — when an ACK's control byte ends one serial chunk and its seq byte opens the next (the EOF ACK is split-prone: slide.asm prints "Transfer complete!" right behind it), the orphaned seq byte (raw binary, usually not a control value) was misrouted to the terminal and never fed to the SM. The framer stayed parked in AfterAckOrNak, the EOF ACK never completed, no file-2 header was ever sent, and both sides waited silently. Second defect found while tracing the stuck chip: keyboard.js's Esc arm used slide-recv's `isSlideActive` (recv-only), so Esc during a SEND session was inert — the wedge had no keyboard escape (the chip's [Cancel] button was the only working cancel, and it is what delivered the "cancelled by peer" CAN to the Z80).

- **UAT-E9-03 round 2 (2026-07-24, retest still failed identically).** The split-ACK fix was real but not the whole story. Downloaded and read the actual `slide.asm` v0.5.2 (the earlier WebFetch-summarized reading had gaps) plus wire-timeline instrumentation of our own sender. The decisive facts: (a) slide.asm's receiver ACKs once per WIN_SIZE=4 frames (`.no_flush`: ACK when seq ≡ 0 mod 4) plus once for the EOF — never per frame; (b) our pump sent ONE frame per inbound dispatch, so after each window ACK we sent one frame and stalled — every hardware send has been limping on the Z80's per-byte retry timeout, which NAKs the expected seq (~660 ms/cycle, MAX_RETRIES 15) and pulls one frame per NAK. Transfers "worked" 4-5× slow, drowning the wire in ACK/NAK control pairs; (c) file 2 of Ant's pair is the first file ≥ 24 KB — frame seq 24 = 0x18 = CTRL_CAN. Once any control pair split across chunks (pre-fix), the parked framer ate the next pair's control byte as a stale seq, the follow-up 0x18 seq byte was then fed at top level as CTRL_CAN, and the SM's mandatory both-roles cancel echo (state.rs:543) sent a real CAN to the Z80 → "Transfer cancelled by peer" → exit — deterministic for 24 KB+ files under NAK spam, impossible for the 19 KB file 1 (max seq 21). The mock bot had masked all of this by ACKing every frame. FLUSH_SIZE == WIN_SIZE × FRAME_SIZE in slide.asm means every disk-flush deaf window sits just before a window ACK, so a sender that sends exactly one window per ACK (slide-py's behavior) is timing-safe by construction — which is also what OUTBOUND_VIEW_CAP (4128 = window + EOF marker) was sized for all along.
