## 1. What shipped

You can now drag a filename out of one MicroBeast's terminal and drop it on the other
one's, in a second Chrome tab, and the file crosses. No server, no changes to the SLIDE
protocol, no firmware changes. The drag itself carries proof of which tab it came from;
the file contents travel over a private channel between the two tabs.

Four stories, all done. They shipped in the order they depended on each other, which
isn't their numbering:

## 2. What went well

**The design decision that mattered most was made before any code.** Asking another tab
for a file has two separate questions in it: "is anyone there?" and "did the file
arrive?" Those need very different amounts of patience — an answer comes back in about 2
milliseconds, but actually pulling the file off a MicroBeast takes many seconds. Bundling
them under one deadline would have meant either giving up on healthy transfers or waiting
forever on dead tabs. Splitting them was decided during planning rather than discovered
during debugging.

**Error messages stayed in one place.** The transport module sends back short codes, never
sentences. Only the drag module turns those into words. That kept every user-facing string
in the one story that had thought about the wording, and it meant the whole set of
messages could be tested directly without needing two real tabs.

**Everything assumes it's broken until proven otherwise.** If a check can't run, the
answer is "refuse", not "go ahead". A damaged message is discarded rather than passed
along to be dealt with later. An unfinished test setup refuses to hand out files instead
of handing out the wrong ones.

**Some tests read the source code itself.** A couple of rules can't be checked by running
the app — "this module must not touch the page directly", "this code must not set up
repeating timers". So there are tests that read the file and fail if those appear. Unusual,
and worth keeping.

**Every story corrected its own plan before writing code.** S11.1 found 3 mistakes in the
epic, S11.2 found 5, S11.3 found 7. Some were significant: the epic named a function three
times that has never existed. This checking step is quietly doing a lot of work.

## 3. The main finding: one bad name, seven near-misses

There's a function that answers "is a file transfer happening right now?" It only knows
about transfers coming *from* the MicroBeast. It's blind to transfers going the other way.

Seven places in the code needed that answer. Each one had to know about the blind spot and
work around it. In E11 alone:

| Where | What happened |
|-------|---------------|
| S11.4's cancel handling | Got it wrong — the review called it "the third time this has happened" |
| S11.2's "is the other beast busy?" check | Got it right, deliberately, noting it had already caught people out three times |
| S11.3's two checks | Got it right, with a test to keep it that way |
| The tab-closing code | **Got it wrong.** Closing a tab mid-send told the MicroBeast nothing, and it sat waiting for a file that was never coming |

That last one was the only defect in the epic that reached a user with nothing catching
it. It had been reported three separate times across three stories and carried forward each
time, because each story had good reasons not to touch that file.

**The lesson isn't "people were careless."** Two of the three noticed and got it right.
The lesson is that a function whose name promises more than it delivers will eventually
meet someone who believes the name. **Fixed today** — see §7.

This is the most valuable habit in the epic and it's written down nowhere. It lives in
whoever happens to be doing the work.

## 5. Third finding: hardware found what tests can't

The E9 retrospective warned that our fake MicroBeast and fake mouse are kinder than the
real ones. E11 ran two hardware checks and both proved it:

- **Your first check** showed that the error message for "that MicroBeast is already open
  in your other tab" was keyed on the wrong error type. Chrome reports something different
  from what the code expected — meaning **that message had never once appeared** for the
  situation it was written for.
- **Your second check** was the first time a real drag between two tabs had ever happened.
  Playwright's fake drags don't go through the browser's real drag machinery, so nothing
  had ever proved the file information survives the trip. It also caught the confirm box
  naming the wrong drive: it said the file was going to drive A: while the receiving
  MicroBeast was on B:. Your call was to delete the drive letter rather than try to fix it.

**A box that states a fact the app doesn't actually have is worse than one that says
less.** Worth keeping.

## 7. What I fixed today

**The tab-closing bug** (`b9827ab`). Closing a tab while sending now tells the MicroBeast
to stop. Both halves fixed: the check that decides whether to act, and the stop command
itself, which was also the receive-only one and would have done nothing.

**One shared answer to "is a transfer running?"** (`d9f9acf`). This was your call and it
was the right one. There were four different hand-written versions scattered around, which
had drifted apart. Now there's one function, with all four things it checks and why each is
needed written at its definition. The misleading function was renamed so its name says
"receive only", which was the actual trap.

Two live bugs fell out of doing that:

- **Pasting during a send** was allowed, and every byte was silently thrown away. You'd
  watch a paste progress bar advance over a paste that sent nothing.
- **The session log** was paused during receives but not sends, so every reply the
  MicroBeast made during a file send was dumped into your log as noise.

Both now do what their own comments always claimed.

**The hunt for unfinished code** (`b71f648`). Found one real thing, and it was a live bug.
A function that adjusts paste speed to match the connection speed was written, exported,
commented as "called from the serial code" — and never called by anything, ever. So paste
speed was permanently tuned for 19200 baud. If you connect at 9600 and paste, the app
pushes bytes at nearly twice the speed the wire can carry them. Now wired up, with a test.

Nothing else was dead. I checked every exported function for callers; eight others are
only used inside their own file, but they're all real working code.

**The comment check** (same commit). Six comments corrected, all the same shape: written
when something genuinely was a placeholder, never updated when the work shipped. Each now
says what it used to be, so the history is still readable.

## 10. Known rough edges, deliberately left

- **A late error message can wipe out a live progress display.** Needs a decision about
  which wins. That's a design call — **yours**.
- **"Already open in another tab" can be wrong.** Chrome reports the same error whether
  another tab has it, another program has it, or you lack permission on Linux. A Linux
  user not in the right group will go hunting for a tab that doesn't exist.
- **The startup message counts the wrong thing.** It says "2 MicroBeasts detected" based on
  whatever you last connected to — so two non-MicroBeast adapters get called MicroBeasts.
- **A tab that's killed outright** (crash, force quit) leaves the other tab waiting
  forever. Deliberately not patched with a polling loop, since that's what S11.4 removed.
- **A very long multi-file drag** silently transfers fewer files than asked, because the
  command line has a length limit. It transfers what fits.
- **Leaving a tab hidden for many minutes** during a transfer is still untested. Your
  hardware check covered about 10 seconds, which exercises the basic case but not Chrome's
  more aggressive slowdown after several minutes.
- **One internal callback is named misleadingly** — it fires even when the file went to the
  Downloads folder rather than the chosen one. The user-visible outcome is still correct;
  only the internal name misleads.
